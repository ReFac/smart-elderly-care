# 长者档案与文书存档

「个人与医疗档案」复用入住时生成的长者档案号。转床后，历史文书、亲属账号及原件继续关联同一人。总管理员在「账号与权限」中创建家属账号并绑定一位长者。家属登录后，在「我的亲属档案」中填写本人资料。

## 登记字段

| 部分 | 必填 | 可补录字段 |
| --- | --- | --- |
| 基础身份 | 档案号、姓名 | 出生日期、出生地、籍贯、登记年龄、现住址、原职业、文化程度、常用语言或方言、婚姻情况。出生日期优先用于计算周岁。 |
| 家庭与经济 | 关联长者 | 兄弟姐妹、子女及照护分工、原居住与照料安排、收入与费用来源、经济补充说明。 |
| 家属自助 | 本人姓名、关系、电话 | 居民身份证号、地址、微信、邮箱和紧急联系说明。身份证号核对长度、出生日期格式与校验位，身份核验另由机构办理。 |
| 医疗记录 | 文书日期、类型、来源、描述 | 待核实事项。CT、其他影像、诊断记录、检验报告、出院小结及其他医疗文书需附 JPEG 或 PNG 原件。手工病史补录可只提交文字。 |

员工按岗位权限获取字段。基本资料维护需要 `intake`，查阅需要 `residents` 或 `intake`。家庭与经济资料另需 `relatives`。亲属本人和总管理员可查阅完整身份证号，有亲属联络权限的员工看到掩码。普通员工无法代替亲属修改该档案。总管理员代录时，服务端从账号表核对家属身份和绑定关系。

## 归档行为

1. 在长者详细档案内选择「存档医疗文书」。填写文书实际发生日期与来源，可从照片库选图或使用手机相机拍摄。单张原件最大 8 MiB，多页资料可逐页归档。
2. 核对并填写原文事实。可采用经人工核对的外部 OCR 转录，也可以手工描述。归档账户即为本次核对人。
3. 提交时一次生成结构化概括，包含文书日期、类型、来源、文字来源、原文事实、待核实事项和核对人。系统保存填写内容和登录身份，形成固定版本。之后打开详情直接读取该版本。
4. 时间线按文书发生日期倒序，同日按入库先后倒序。详情可查存档日和照片原尺寸。存档时写入的 BLOB 与上传字节一致，原件、摘要和审计记录在同一事务提交。

护士核实后的跌倒处置进入同一长者的「护理复核与历史摘要」，保留发生时间、房间、复核人和处置说明。

## 接口

| 方法 | 用途 | 权限 |
| --- | --- | --- |
| `POST /api/commands · dossier.profile` | 用 `residentId` 编辑基础登记及获准的家庭字段 | `intake`。涉及家庭经济时同时需要 `relatives` |
| `POST /api/commands · dossier.relative` | 家属编辑自己的联系方式、证件和关系。业主可代录已绑定账号 | 家属本人、总管理员 |
| `POST /api/commands · dossier.document` | 校验、留存原件及首次概括 | `medical.write` |
| `GET /api/documents/{id}/image` | 按服务端会话授权返回原始 JPEG 或 PNG | `medical` |
| `GET /api/state` | 读取按岗位投影的 `dossierProfiles`、`medicalDocuments`、`relativeProfiles` | 服务端逐集合、字段核对 |

归档命令传入 `requestId`、`residentId`、`eventDate`、`category`、`source`、`description` 和可选 `pending`。有照片时传 `imageBase64`，可附 `mime` 与 `filename`。客户端收到数据版本冲突后，先读取最新快照，再决定是否用原请求编号提交。相同输入复用现有文书，相同原件带不同描述时返回校验错误。系统为同一张图在不同长者名下分别留存证据。

医疗文书表存储 SHA-256、原图和概括版本。读取列表只查询元数据，数据库触发器阻止应用更新或删除已归档行。原件归档的持久性还取决于 SQLite 文件的备份和恢复。

OCR 与 DeepSeek 接口留给后续适配。当前工作台以人工描述或已核对的转录生成概括，归档过程没有外部模型调用。接入时，适配器应使用归档请求编号、原件哈希和登录权限，保存一次生成结果并交由人工核对。模型凭据由平台运营方保管，机构总管理员可查看套餐。当前真实 DeepSeek 调用限于 Agent 委派规划。
